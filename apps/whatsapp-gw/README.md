# WhatsApp gateway

The process that owns the WhatsApp connections. It is a Go module of its own —
`github.com/anakbolu/timbolu/apps/whatsapp-gw` — because a WhatsApp session is
a socket that stays open: the API serves requests and may be replaced at any
moment, and a linked number whose connection dies with the request that touched it
is a number that is never online.

It imports `packages/` and **never** the backend. The two processes talk over HTTP
on an address the public never reaches.

## What it owns

- The WhatsApp socket, through `whatsmeow` (`internal/engine`).
- The sealed device state, one blob per number (`internal/sealer`, the
  `whatsapp_sessions` table).
- The fleet directory it follows — which tenants have a number to serve
  (`whatsapp_directory`, read unscoped, because a fleet worker has to discover the
  tenants before it can open any workspace's scope).
- The media bytes, in the same object storage the backend uses.
- The session lease, in Redis: one number has one owner, and the lease is what
  keeps two processes off one session.

## What it does not own

- When a message may leave. The product decides that — the pacing, the hourly
  ceiling, and the approval gate are all above this process.
- The numbers, the messages, the outbox, and the directory's writes. Those are the
  backend's, and the gateway reaches them through the seam rather than the schema.

## Layout

```
cmd/wa-gateway/         # main: the seam listener and the engine's loops
internal/
  container/            # the only place that calls constructors; the ops listener
  engine/               # whatsmeow: the transport, the device store, the lease
  sealer/               # seals a device blob with the workspace's own data key
  media/                # the bytes of what a customer sent, in object storage
  repository/           # sqlc over whatsapp_sessions, whatsapp_directory,
                        # and workspace_keys (read-only)
  repository/sqlcgen/   # generated by `make sqlc` from queries/whatsapp.sql
Dockerfile              # built with the repository root as the context
scripts/coverage.sh     # the module's own 80% gate
```

## Commands

```bash
make wa-gateway      # run the gateway on the host
make test-gateway    # go test ./... (the repository tests need Docker)
make cover-gateway   # tests + the 80% coverage gate
make sqlc            # regenerate the query code (backend and gateway)
```

## The two seams

One shared secret, `WA_GATEWAY_TOKEN`, authenticates both directions, and both map
an error to an HTTP status through one table in `packages/whatsapp/seam`, so a
refusal reads the same whichever way it crosses.

| Direction | Listener | Env | For |
| --- | --- | --- | --- |
| API → gateway | the gateway's `WA_ADDRESS` | `WA_GATEWAY_URL` | Send a message, link or unlink a number, read a number's state |
| gateway → API | the API's `INTERNAL_ADDRESS` | `WA_API_URL` | Record an inbound message, claim the outbox, report a number's status, mark it paired |

The API's internal listener is never published: it speaks for every tenant at once,
authenticates with the one secret, and reads the workspace from the `X-Workspace-Id`
header rather than from a user's session.

## Configuration

The gateway reads the same `packages/platform/config` as the backend. The settings
that are its own:

| Variable | What it is |
| --- | --- |
| `WA_ADDRESS` | Where the seam listener binds (default `:8090`); the API reaches it here |
| `WA_API_URL` | Where the gateway reaches the API's internal seam (compose: `http://api:8091`) |
| `WA_GATEWAY_TOKEN` | The shared secret both directions authenticate with |
| `WA_OWNER` | This instance's name in the session lease; empty for a single instance |
| `WA_HOURLY_LIMIT` | The default send ceiling per number; zero takes the product default |
| `WA_LOG_WHATSMEOW` | whatsmeow's own protocol log, for debugging |
| `OPS_ADDRESS` | Where the probes (`/health`, `/ready`, `/metrics`) are served |

It needs `DATABASE_URL`, `REDIS_URL`, `KMS_MASTER_KEY`, and `STORAGE_DRIVER` like
the backend does. It does **not** need Temporal: the gateway has no workflows.

## Probes and shutdown

`/health` never touches a dependency; `/ready` checks every configured one. On
shutdown the engine stops first and releases its leases, which is what makes a clean
restart a takeover in milliseconds rather than a wait for the TTL — and what keeps
two processes from holding one session. The server is given its grace afterwards.

See [`docs/deployment.md`](../../docs/deployment.md) for the image and the release
order, and [`apps/backend/README.md`](../backend/README.md) for the product half.
